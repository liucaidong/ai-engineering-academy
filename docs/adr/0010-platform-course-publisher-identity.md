# ADR-0010: Isolated platform identity for immutable course publication

- Status: Accepted
- Date: 2026-11-10
- Scope: global course catalog publication and its security/audit boundary

## Context

Course releases are global catalog snapshots, not tenant-owned learner data.
Tenant membership and the tenant_admin role must not imply authority to
publish globally visible course content. The existing audit_events table is
FORCE-RLS protected; its tenant-user insert policy requires an authenticated
actor_user_id equal to the transaction-local user identity. A platform
publication is not a learner or tenant-user action, so fabricating a user ID
would corrupt the audit principal and weaken the trust boundary.

The existing course release service already builds draft snapshots, computes a
deterministic SHA-256 digest over canonical UTF-8 JSON, and validates a
draft-to-published transition. The frontend Zod CourseSchema is the canonical
course contract and includes nested strict objects and cross-record integrity
checks. A backend publication boundary must validate again rather than trust
a browser-generated artifact.

## Decision

1. Global publication is performed by a dedicated PostgreSQL login role named
   academy_course_publisher, separate from the API runtime, tenant users and
   tenant administrators.
2. The publisher role must be NOSUPERUSER, NOBYPASSRLS, NOCREATEDB,
   NOCREATEROLE, NOINHERIT, and must not be a member of another role.
   Connections are accepted only when both session_user and current_user
   equal the dedicated role.
3. The role receives only SELECT and INSERT on course_releases, and
   INSERT on audit_events. It receives no UPDATE, DELETE, TRUNCATE, CREATE,
   identity, tenant, or learner-record privileges. The existing audit insert
   policy evaluates a membership EXISTS subquery, so the role receives SELECT
   on tenant_memberships solely for policy evaluation; a restrictive RLS policy
   denies it every row, including when the role sets arbitrary custom GUC values.
4. Migration 0012_platform_publisher_audit adds a narrow FORCE-RLS-compatible
   audit insert policy. It accepts only the dedicated database role with
   actor_user_id IS NULL and tenant_id IS NULL. It does not weaken or
   replace tenant-user audit policies.
5. A database trigger prevents the publisher role from inserting drafts and
   prevents published/retired snapshots from being changed or deleted.
   Published releases may transition only to retired; retired releases cannot
   be reactivated.
6. The exporter loads all course modules through the application's Vite SSR
   loader and validates the result with the same Zod CourseSchema used by the
   frontend. The backend then validates the JSON again with a strict Pydantic
   schema that rejects unknown fields, invalid nested values, duplicate IDs,
   unknown prerequisites/labs and prerequisite cycles.
7. Publication requires an explicit --expected-sha256 obtained from a prior
   dry-run. The CLI checks the snapshot's version, recomputes the canonical
   digest, verifies the direct database role, and inserts the immutable release
   and global audit event in one transaction.
8. The unique (course_key, version) constraint is the concurrency boundary.
   An identical already-published release is an idempotent no-op; any existing
   release with a different digest, schema version or lifecycle state is a
   hard conflict. Publication never overwrites an existing snapshot.
9. The audit event has null user and tenant IDs. Its metadata records the
   dedicated database role, release UUID, course key/version, schema version,
   digest and request ID. This records the database principal, not a verified
   individual human operator; stronger human attribution requires a future
   platform identity and approval workflow.

## Consequences

- tenant_admin cannot publish global catalog releases.
- The learner API runtime credential cannot publish or mutate course releases.
- Platform publishing can be exercised without enabling OIDC or learner APIs.
- A release UUID is generated by the backend and is returned only after the
  transaction commits.
- Production use still requires DBA provisioning, secure secret distribution,
  database network restrictions, backup/restore controls and an operator
  approval process. The publisher role credential must not be distributed to
  browser clients or general application workloads.
- This ADR does not implement a general course-authoring UI, instructor
  permissions, or an HTTP publishing endpoint.
