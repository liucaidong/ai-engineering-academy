# M20 Capstone 实验工作簿：端到端 AI 工程项目交付

> 课程版本：0.40.9

> **证据等级：** Capstone 按 E0–E5 逐条评级；Gate 2 至少要求冻结版本 E3 Local-tested；E4/E5 只有在真实目标环境/生产观测证据存在时才可声明。 统一定义见[全课程证据等级](../CURRICULUM_EVIDENCE_LEVELS.md)。

> 五项实验对应 Capstone 五个 Gate。所有模拟数据必须标注；没有实际执行的项目能力不得标记为 tested 或 production-ready。

## Capstone 交付原则

- 以用户任务和可验证业务结果定义项目，不以模型 Demo 作为唯一目标。
- 每项需求必须映射到设计、实现、测试和证据。
- 每项技术决策必须记录替代方案、后果和复审条件。
- Mock、模拟、静态审阅、本地测试、目标环境测试和生产观测是不同证据等级。
- 未验证、受阻和已知风险必须明确披露。

## Gate 0：项目章程与需求基线

**对应课程：** 第一讲《Capstone 立项——需求、范围与验收》

### 实验任务

为一个 AI 客服/合同审查/科研助理项目建立章程和验收追踪矩阵。

### 操作

1. 识别用户、数据主体、审批者、运营者和外部依赖。
2. 定义问题、当前替代流程、失败成本、目标和非目标。
3. 为需求分配唯一 ID、优先级、owner、验收条件和验证方法。
4. 建立风险登记表、数据许可清单和依赖清单。
5. 运行 `01_requirements.py`，检查需求字段、重复 ID 和追踪覆盖。

### 必须提交

- 项目章程；
- 需求/非目标列表；
- Definition of Ready/Done；
- 需求—测试—证据矩阵；
- 风险、数据许可和外部依赖登记。

### Gate 通过条件

没有明确用户任务、可测量验收指标、数据授权或高风险 owner 的项目不得进入实现阶段。

## Gate 1：架构包与 ADR

**对应课程：** 第二讲《系统架构、数据流与技术决策》

### 实验任务

为 Capstone 设计组件、数据流、信任边界和架构决策。

### 操作

1. 绘制 Context/Container/Component 和关键时序视图。
2. 对模型、RAG、Agent/Workflow、工具、数据存储和部署方案进行选型比较。
3. 将关键架构约束转成 fitness functions 或 contract tests。
4. 至少编写三份 ADR，记录候选方案、决策、后果和复审条件。
5. 运行 `02_architecture_review.py`，检查 ADR 完整性和状态。

### 必须提交

- 架构图、数据流和时序图；
- 信任边界和身份传播图；
- 数据分类、许可、保留和删除规则；
- ADR 集；
- 架构约束与接口契约测试计划。

### Gate 通过条件

架构图必须与计划实现相匹配；每项关键选择均有理由、替代方案和验证计划。

---

## Gate 2：垂直切片与工程实现

**对应课程：** 第三讲《模型、RAG、Agent 与工具集成》

### 实验任务

交付一个可运行、可追踪的最小端到端用户旅程。

### 操作

1. 先选一条用户路径贯穿 UI/API/domain/data/model/retrieval/tool/audit。
2. 为模型、检索和工具定义契约、版本、错误语义和超时。
3. 建立单元、组件、契约、集成和少量 E2E 测试。
4. 区分 mock、sandbox 和真实 provider；记录构建 commit 与依赖锁。
5. 运行 `03_vertical_slice.py`，检查正常、失败和安全拒绝轨迹是否齐全。

### 必须提交

- 可运行代码和 README；
- API/schema 与模型/Prompt/工具/索引版本；
- 正常、失败、安全拒绝三类执行轨迹；
- 分层测试结果；
- Mock/真实服务边界和未验证项。

### Gate 通过条件

至少一条真实可复现的垂直切片通过验收；若受凭证或环境限制，只能标记 blocked/not tested，不得虚构集成完成。

## Gate 3：综合评测、安全和运行验收

**对应课程：** 第四讲《综合评测、安全、监控与部署》

### 实验任务

构建 Evidence Matrix，将需求和风险映射到控制、测试、证据和决策。

### 操作

1. 建立正常、边界、对抗、故障、恢复和人工接管用例。
2. 覆盖 Prompt Injection、越权、跨租户、敏感数据、工具重放和供应链风险。
3. 分层报告检索、引用、任务成功、工具 schema、安全、延迟和成本指标。
4. 定义 SLO、硬性安全门槛、容量假设、告警和回滚条件。
5. 运行 `04_evidence_matrix.py`，检查风险覆盖和证据等级。

### 必须提交

- Benchmark 与回归报告；
- 威胁模型、红队用例和实际阻断证据；
- Trace/Metrics/Logs 与隐私策略；
- SLO、容量和成本报告；
- 部署、回滚和事故响应计划。

### Gate 通过条件

硬性安全约束必须单独通过；没有证据的风险不得被标记为已解决。

---

## Gate 4：交付、演示和技术答辩

**对应课程：** 第五讲《项目交付、演示与技术答辩》

### 实验任务

冻结可复现版本，准备证据索引、演示脚本、答辩和后续路线图。

### 操作

1. 冻结 commit、依赖锁、模型/Prompt/工具/索引/策略版本和演示输入。
2. 生成 evidence index，引用测试报告、真实日志、trace 和业务状态。
3. 演示正常完成、部分失败、人工接管/安全拒绝。
4. 解释关键决策、替代方案、成本、残余风险和未验证项。
5. 运行 `05_defense_readiness.py`，检查交付清单和证据等级。

### 必须提交

- 最终交付目录和可复现说明；
- 演示脚本与 evidence index；
- 技术答辩材料；
- 已实现/已审阅/已测试/未验证/受阻清单；
- 责任人、期限和后续路线图。

### Gate 通过条件

答辩结论必须与证据等级一致。Capstone 通过不等于生产认证，生产上线仍需独立安全、隐私、运维和业务批准。

## 统一评分建议

| 维度 | 权重 | 证据 |
|---|---:|---|
| 需求和项目治理 | 15% | 章程、需求追踪、风险/依赖 |
| 架构和决策 | 20% | 架构视图、信任边界、ADR |
| 工程实现 | 25% | 垂直切片、契约、测试和执行轨迹 |
| 评测与安全 | 25% | Benchmark、威胁模型、SLO 和证据矩阵 |
| 交付与答辩 | 15% | 可复现演示、证据索引、残余风险披露 |

## 最终审查清单

- 是否存在无法追踪到测试的关键需求？
- 是否存在没有 owner 的高风险？
- 是否把 mock 或模拟误写为真实集成？
- 是否只展示成功路径而没有失败/拒绝路径？
- 是否将平均质量掩盖了安全硬约束？
- 是否冻结了模型、Prompt、工具、索引和策略版本？
- 是否把未验证能力清楚标记并给出后续计划？


## Capstone 证据等级与不可补偿门槛

### 证据等级

| 等级 | 标签 | 证据定义 | 不允许推断 |
|---|---|---|---|
| E0 | Designed | 设计、伪代码、测试计划 | 不证明实现或运行 |
| E1 | Static-reviewed | 静态审阅、Schema、类型或格式检查 | 不证明运行行为 |
| E2 | Simulated/Mock | 合成数据、Mock Provider、确定性模拟 | 不证明外部服务集成 |
| E3 | Local-tested | 冻结版本在本机重复执行并通过指定测试 | 不证明目标环境或生产表现 |
| E4 | Target-env-tested | 目标环境或真实 Sandbox 测试 | 不证明长期生产表现 |
| E5 | Production-observed | 有时间窗口的生产流量、指标和运营证据 | 不证明未来版本或其他流量分布 |

证据等级是课程评价约定，不是行业认证。每项证据必须记录版本、环境、输入、命令/步骤、结果、时间和限制。不得把设计图、静态审阅或一次 Demo 标记为 E3/E4/E5。

### Gate 2 最低工程门槛

- 至少一条端到端用户旅程在冻结版本上达到 E3 Local-tested；
- 展示正常、失败恢复和安全拒绝/人工接管三条路径；
- 对关键写操作验证服务端授权、幂等或状态核验；
- 外部 Provider 不可用时，可以用本地可执行替代路径验证内部契约，但外部集成必须标记 blocked/not tested；
- Mock、Sandbox、真实 Provider 和生产环境证据必须分开列出。

### 不可补偿的安全与证据门槛

以下任一情况失败，Capstone 不通过，不能用总分或演示效果抵消：
1. 关键越权、跨租户数据泄漏或未经授权的副作用操作未被阻断；
2. 关键写操作没有幂等/状态核验策略；
3. 将 Mock/模拟/静态审阅伪称真实集成或生产测试；
4. 隐瞒重大失败、未验证能力或已知高风险；
5. 关键需求没有验收条件或证据引用。

### Capstone 通过门槛

建议总分至少 75/100，且 Gate 0–4 全部通过、无未关闭 P0、无安全硬门槛失败、至少一条端到端路径达到 E3、关键需求均有验证证据。75 分是课程教学门槛，不是行业认证或生产上线许可。
