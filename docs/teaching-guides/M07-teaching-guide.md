# M07 教师教学指南与作业参考解答

> 课程版本：0.40.9

> **证据评阅：** 教师应按[全课程证据等级](../CURRICULUM_EVIDENCE_LEVELS.md)区分设计、静态审阅、模拟/Mock、本地测试、目标环境测试和生产观测；只为实际覆盖范围授予等级。

> 用于教师备课、助教批改和学生复习；参考解答不是唯一可接受答案。

## 使用方式

- 建议每讲 75–90 分钟；先从真实案例提出问题，再推导机制，最后审阅工程证据。
- 课前让学生写下假设；课堂结束前提交公式、架构图、状态图、测试记录或决策日志。
- **教学主线：** 工具调用是模型提出意图、宿主校验授权并执行、再回传结果的受控协议。
- 评分先检查边界、假设、单位、失败路径和证据，再检查表达完整性。

## 模块先修与教学准备

- **先修知识：** HTTP、JSON、类型系统、事务与权限模型
- **教师准备：** 准备一个最小正例、一个失败案例和一份可审计输出；区分模型推断、宿主控制、业务规则与外部系统状态。
- **贯穿案例：** 结构化输出与 Tool Calling 的作业均要求说明输入、状态、权限、输出、成本和异常处理。

## 第一讲：Tool Calling 协议与控制流

### 课前准备

- 复习：HTTP、JSON、类型系统、事务与权限模型
- 预读主题：工具调用不是模型直接执行代码、工具调用状态机、结果回传与多轮交互、错误与取消语义、复现练习：追踪一次带超时的工具调用。
- 准备一个成功路径和一个失败路径，要求学生比较其状态、权限和恢复差异。

### 教学路径与关键讲解

1. **概念建立：** 讲解 工具调用不是模型直接执行代码、工具调用状态机、结果回传与多轮交互，先定义对象、边界和数据流。
2. **工程深化：** 以 错误与取消语义 为切入点讨论异常、权限、成本或可维护性，并指出由哪个可信组件执行控制。
3. **实践复现：** 复现练习：追踪一次带超时的工具调用。先独立推导，再对照参考解答检查假设与边界。
4. **证据要求：** 提交物包含输入/假设、处理步骤、结果、失败路径、版本和未验证项。

### 学习检查点（含教师提示）

- **核心机制：** 围绕「工具调用不是模型直接执行代码」与「工具调用状态机」，能否解释本讲的关键机制并写出必要公式、状态或数据流？要求说明变量/参与方及适用假设。
- **工程权衡：** 针对「结果回传与多轮交互」与「错误与取消语义」，能否比较不同实现的质量、成本、延迟或安全取舍，并说明何时不应采用？
- **验证与失效：** 围绕「复现练习：追踪一次带超时的工具调用」和「协议层次：Function Calling、MCP Tools 与 JSON-RPC」，能否设计一个边界/故障/对抗测试，明确预期结果、证据和通过标准？
### 课后复习

- 不看讲义重画本讲数据流/状态图，并逐项标记可信边界。
- 为一个失败案例写出根因、检测信号、恢复动作和防复发测试。
- 将结论转化为一条可自动检查的验收条件。

### 正式作业参考解答

**原始作业：** 为订单查询和退款工具画出完整状态机，标记模型、宿主、授权服务和外部 API 的责任边界。

**参考解答与推理：** 状态机包含 proposed、schema_validated、authorized、awaiting_confirmation、executing、succeeded、failed、cancelled、unknown。模型只提出 tool name/arguments；宿主分配 call_id，校验 schema 和业务约束，再调用授权服务。超时后若无法确认外部结果，应进入 unknown 并按 request_id 查询，不得盲目重放退款。

**原始 Rubric 对照（满分 10 分）：**

- **控制流（4 分）：** 完整描述提出、验证、授权、执行和回传。要求提交物中有直接证据支持该项结论。

- **状态模型（3 分）：** 状态和 call_id/request_id 设计明确。要求提交物中有直接证据支持该项结论。

- **失败语义（3 分）：** 覆盖超时、取消、重复执行和错误分类。要求提交物中有直接证据支持该项结论。

**常见错误与纠正：**

- 把 tool call 当作已执行；把 schema valid 当成授权；超时后盲目重试写操作；将模型选择当作权限控制。
- 只写术语、不展示推导或数据来源；要求补充中间步骤和可复核依据。
- 把设计、模拟和真实执行混为一谈；要求显式标注验证等级。

4. **证据要求：** 提交物包含输入/假设、处理步骤、结果、失败路径、版本和未验证项。

### 正式作业参考解答

**原始作业：** 定义一个订单退款工具的 JSON Schema，并写出 schema、订单归属、金额上限、权限和幂等键校验顺序。

**参考解答与推理：** Schema 定义类型、required、enum、范围、格式及 additionalProperties 策略；随后执行对象级授权、订单归属、可退款余额、币种/精度、订单状态和幂等键校验。金额用整数最小货币单位或定点数，拒绝负数、超额和未知字段。schema_valid 不等于业务合法或有权执行。

**原始 Rubric 对照（满分 10 分）：**

- **字段契约（3 分）：** 字段类型、必填、范围、币种和额外字段策略完整。要求提交物中有直接证据支持该项结论。

- **业务验证（4 分）：** 验证订单归属、可退款余额和状态。要求提交物中有直接证据支持该项结论。

- **安全边界（3 分）：** 参数化访问、授权和幂等控制明确。要求提交物中有直接证据支持该项结论。

**常见错误与纠正：**

4. **证据要求：** 提交物包含输入/假设、处理步骤、结果、失败路径、版本和未验证项。

### 正式作业参考解答

**原始作业：** 为 30 个企业工具设计分层注册表和路由策略，给出只读/写入分组、风险等级、选择评测指标和服务端拒绝规则。

**参考解答与推理：** 注册表按只读查询、低风险写入、高风险资金/外部动作分组。每项含稳定 tool_id、版本、JSON Schema、scope、风险级别、超时、幂等语义、owner 和审计策略。评测混淆矩阵、参数完整率、误调用成本；宿主 allowlist、对象授权、速率限制和高风险确认必须独立于模型路由。

**原始 Rubric 对照（满分 10 分）：**

- **注册表（3 分）：** 包含 ID、版本、schema、scope 和风险元数据。要求提交物中有直接证据支持该项结论。

- **执行门禁（4 分）：** 实现 allowlist、授权、确认和限流。要求提交物中有直接证据支持该项结论。

### 正式作业参考解答

**原始作业：** 设计一个会创建退款并调用支付网关的工具，说明幂等键、事务边界、超时查询、Saga 补偿和审批绑定。

**原始 Rubric 对照（满分 10 分）：**

- **事务设计（4 分）：** 区分本地事务、outbox 和跨服务补偿。要求提交物中有直接证据支持该项结论。

- **审计审批（3 分）：** 审批绑定参数并保留可追溯记录。要求提交物中有直接证据支持该项结论。

- **指标（4 分）：** 分层计算选择、参数、授权和结果指标。要求提交物中有直接证据支持该项结论。

- **证据边界（3 分）：** 明确模拟/沙箱/provider-backed 验收范围。要求提交物中有直接证据支持该项结论。

**常见错误与纠正：**

- 把 tool call 当作已执行；把 schema valid 当成授权；超时后盲目重试写操作；将模型选择当作权限控制。
- 只写术语、不展示推导或数据来源；要求补充中间步骤和可复核依据。
- 把设计、模拟和真实执行混为一谈；要求显式标注验证等级。

## 进阶概念辨析与课堂扩展

### 1. API Tool Call、Host Runtime、MCP 和 JSON-RPC 是不同层次

Provider API 定义模型如何表达工具调用；Host Runtime 决定如何解析、校验、授权、执行和回传；MCP 定义 Client/Server 的能力发现与工具调用协议；JSON-RPC 定义请求、响应和错误 envelope。Provider function call 不会自动成为 MCP 请求。Adapter 必须映射 call ID、request ID、错误、取消和 deadline。

### 2. Strict Schema 是 provider-specific 子集

不同模型 API 对 JSON Schema 支持范围不同。某些 strict mode 要求 additionalProperties=false、所有 properties 均 required，并以 nullable 表达可选语义。建立 compatibility matrix，覆盖 nested objects、enum、range、array bounds、$ref、oneOf、format、nullable 和版本迁移。即使模型严格遵循 Schema，服务端仍要执行领域规则和授权。

### 3. 动态工具发现与程序化调用的优化目标不同

Tool Search/Deferred Loading 减少初始工具定义 token 和候选歧义；Programmatic Tool Calling 让受控代码处理循环、并行、条件和中间结果，减少模型往返与上下文污染；Tool Use Examples 补充 Schema 难以表达的调用习惯。它们会增加发现延迟、代码执行面和错误恢复复杂度，需要 sandbox、allowlist、预算、deadline 和审计。参考 Anthropic 2025 年 advanced tool use 资料时，应区分其产品/API 特性与通用协议概念。

### 4. Timeout、Unknown 和 Retryable 不能混用

Timeout 是观测到的通信/等待事件，不代表业务失败。若无法确认外部副作用状态，应标记 unknown 并通过稳定 idempotency key 查询。Problem Details（RFC 9457）可提供机器可读错误 type/title/status/detail/instance 和扩展字段。重复请求需绑定 principal、参数摘要和幂等键；相同 key 不同参数应拒绝。

### 5. 工具验收要按证据等级报告

静态 Schema 检查、mock 状态机测试、sandbox API 合约测试、provider-backed 集成和生产 canary 覆盖不同风险。工具选择准确率不能替代授权违规率；执行成功不能替代业务结果成功；模拟通过不能声称真实外部集成通过。每次验收固定模型、Prompt、工具 Schema、provider API 版本、数据集和执行模式。

## 评分与教学一致性要求

- 评分项和分值逐条取自课程模块正式 Rubric；不改变原题、分值或课程内评分标准。
- 数学题写明单位、假设和舍入规则；架构题展示替代方案与故障边界；安全题将控制映射到执行组件和测试证据。
- 外部服务使用 mock/sandbox 时明确标注范围，不得将模拟通过描述为真实 provider 或生产验收。
- 允许其他等价方案，只要满足原始 Rubric 且证据充分。


### 协议与幂等补充核验（2026-11-10）

- JSON-RPC request id 是请求/响应关联标识，不是业务幂等键；provider call_id、MCP request id 和 idempotency_key 应分属不同命名空间。MCP 2026-07-28 的真实请求必须包含必要 `_meta` 字段，规范页面的简化示例省略了这些元数据。
- Stripe API v1/v2 的幂等行为和 key 清理策略存在差异；教学时不得把某一版本的首次响应缓存、24 小时后可清理等规则推广为所有供应商的通用保证。
- Transactional Outbox relay 可能重复发布；消费者仍需基于 event_id 去重并保持幂等。
- ToolBench 是 ToolLLM 论文中的数据集/评测体系，不是 arXiv:2307.16789 当前论文标题；已统一更正为 ToolLLM。
