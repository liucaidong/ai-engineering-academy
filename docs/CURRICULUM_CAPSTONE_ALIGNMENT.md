# M20 Capstone 与 M01–M20 能力映射及验收门槛

## 1. Capstone 定位

Capstone 是综合工程能力的证据展示，不是把所有课程技术强行堆到一个产品中。项目必须从真实用户问题和数据授权出发，选择必要的模型、检索、Agent、工具、协议、工作流和平台组件；对不采用的技术，提交“不采用理由”和风险分析。

## 2. M01–M20 能力映射

## 3. 五个 Gate 的增强验收标准

### Gate 0 — 项目章程与需求基线
- 每条关键需求有唯一 ID、用户/业务价值、优先级、owner、可观察验收条件和验证方法。
- 明确数据来源、许可、敏感级别、保留/删除和外部依赖。
- 指标写明分子、分母、时间窗和排除规则。
- 高风险需求和安全约束不得作为普通 backlog 项延后。

### Gate 1 — 架构包与 ADR
- 至少有 Context/Container/Component 视图、数据流和关键时序。
- 标记身份传播、信任边界、数据分类、外部服务和故障域。
- 至少三份 ADR；每份包含背景、候选方案、决定、后果、验证计划和复审触发。
- 为不采用 MCP、Skills、多 Agent、微调或多模态等技术提供合理依据。

### Gate 2 — 垂直切片与工程实现
- 至少交付一条在冻结版本上可本地重复执行的端到端用户旅程；若外部凭证不可用，提供真实可执行的本地替代路径，并将外部集成标记 blocked/not tested。
- 旅程覆盖项目实际需要的 UI/API/domain/data/model/retrieval/tool/audit 组件，不要求所有项目都必须有 UI 或 RAG。
- 必须展示正常、失败和安全拒绝三类轨迹。
- 工具写操作必须有服务端授权、幂等或状态核验；模型输出不得作为授权依据。
- Mock/sandbox/真实 provider 分开标记；不得将 mock 通过描述为真实集成。

### Gate 3 — 综合评测、安全和运行验收
- Eval set 记录版本、来源、分层、污染控制和预期答案/评分规则。
- 报告组件级和端到端指标；统计指标说明样本数、区间或适用限制。
- 安全测试至少覆盖注入、越权、跨租户、敏感数据、工具重放和供应链中与项目相关的风险。
- 关键安全硬门槛单独判定；未通过时不得用平均质量分抵消。
- 提交 Trace/Metrics/Logs、SLO、成本、容量、告警、降级、恢复和回滚证据。

### Gate 4 — 交付、演示和技术答辩
- 冻结 commit、依赖锁、模型、Prompt、工具、索引、策略和演示输入。
- 演示正常完成、失败恢复、安全拒绝/人工接管。
- 提交 evidence index，每条关键需求链接到实现、测试和运行证据。
- 逐项标记 Designed、Static-reviewed、Mock、Local-tested、Target-env-tested、Production-observed。
- 明确残余风险、未验证事项、责任人和下一步计划。

## 4. 最终评分

沿用 M20 工作簿 100% 结构：需求/治理 15%，架构/决策 20%，工程实现 25%，评测/安全 25%，交付/答辩 15%。每一项必须引用 Evidence Matrix 中的证据 ID。

**通过条件：**
- 总分至少 75/100；
- Gate 0–4 全部通过；
- 无未关闭 P0；
- 无关键安全硬门槛失败；
- 至少一条端到端路径达到 E3 Local-tested；
- 所有关键需求都有验证方法和证据；
- 所有未验证/受阻事项已披露。

75 分是课程建议的教学门槛，不是行业认证标准。项目生产上线仍须经过独立的安全、隐私、法律、业务和运维审批。

## 5. 证据矩阵最小字段

requirement_id, risk_id, design_ref, implementation_ref, test_id, test_environment, evidence_level, result, timestamp, artifact_digest, owner, limitation。

若一条需求没有实现或测试证据，应标记设计阶段或未验证，不得写“已完成”。
