## Key corrections and qualifications

1. **ISO/IEC/IEEE 29148:** Edition 2 (2018) was confirmed in 2024 and remains the current published International Standard. ISO marked it for revision on 2026-02-16. DIS Edition 3 is in the enquiry phase and will replace the 2018 edition; it is a draft, not an approved published standard, and ISO does not state a fixed publication date.
2. **MCP:** Capstone references are pinned to the 2026-07-28 specification. The release introduces a stateless protocol core, per-request version/capability metadata, optional discovery, header-based routing, authorization hardening and a formal extensions framework. Do not assume older `initialize`/session semantics apply to this version.
3. **SLSA:** v1.2 is the current Approved specification as of this review, superseding v1.1. It includes Build and Source tracks. Provenance/attestation provides verifiable information about artifact origin and build inputs; a version string or unsigned manifest alone is not provenance verification.
4. **OWASP:** GenAI LLM Top 10 2026 is a GenAI/LLM risk taxonomy and should inform, not replace, a system-specific threat model. ASVS 5.0.0 is a stable set of verifiable web-application/service security requirements; it is not an AI-specific risk catalog. Use both with scope clearly separated.
5. **OpenTelemetry:** The concepts documentation covers context propagation and signals (traces, metrics, logs), but generic docs do not prove a specific deployment is correctly instrumented, sampled or privacy-safe. GenAI semantic conventions have their own maturity status and should be pinned separately.
6. **C4 and arc42:** C4 provides audience-appropriate diagrams; not every system needs all levels. arc42 is a tailorable 12-section architecture documentation template, not a mandated standard.
7. **ADR:** The MADR template supports context, decision drivers, options, outcome, consequences and confirmation. A completed ADR records rationale; it does not prove implementation follows the decision.
8. **Testing:** The Practical Test Pyramid distinguishes fast unit tests, integration tests at boundaries and broader end-to-end tests. It is a heuristic for feedback and confidence, not a fixed numerical ratio. E2E tests are useful but may be flaky and expensive.
9. **Provider and framework docs:** OpenAI API and LlamaIndex docs are living references. Pin endpoint/model/SDK versions in project evidence; current quickstarts do not establish a deployed integration.
10. **NIST AI RMF:** The framework is voluntary and under revision; the Playbook is voluntary guidance, explicitly not a checklist.
11. **Capstone evidence scripts:** The examples validate metadata shape, trace links, evidence-grade labels and hard-gate logic. They do not authenticate source artifacts, verify signatures, inspect logs, run security tests or approve production releases.
