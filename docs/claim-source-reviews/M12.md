## 1. Protocol architecture and versioning

| Source | Claim supported | Qualification |
|---|---|---|
| [MCP Architecture](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture) | Defines Host, Client and Server as logical roles; Host owns user-facing policy, Client performs protocol communication and Server exposes capabilities. | An SDK Client object or HTTP connection is not the same as a wire-level protocol session. |
| [JSON-RPC 2.0](https://www.jsonrpc.org/specification) | Requests have ids, notifications omit ids, responses correlate by id and errors contain code/message/data. | JSON-RPC success does not prove business postconditions or authorization. |
| [MCP Specification 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28) | The modern revision removes `initialize`/`initialized` and protocol-level `Mcp-Session-Id`; each request carries version and client capabilities in `_meta`. | Legacy 2025-11-25 and earlier retain the handshake/session model. | [Versioning and Compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) | Modern requests carry version metadata per request; Server implements `server/discover`, which clients may call before other operations; version mismatch reports supported versions. | `clientInfo` is optional, self-reported metadata for display/debugging, not a security signal. The server method is required; the client call is optional. |

## 3. Transport, HTTP and multi-round-trip requests

| Source | Claim supported | Qualification |
|---|---|---|
| [MCP Python SDK: Running Your Server](https://py.sdk.modelcontextprotocol.io/run/) | The official Python SDK documents stdio for local subprocess communication and Streamable HTTP for remote deployment; legacy SSE remains only for older clients. | Transport choice does not replace authentication, network controls or application state design. |
| [HTTP Semantics, RFC 9110](https://www.rfc-editor.org/rfc/rfc9110) | Defines HTTP methods, status codes, fields and request/response semantics used by the MCP binding. | MCP adds protocol-specific headers and JSON-RPC semantics. |
| [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) | Modern clients POST each JSON-RPC request independently; server returns JSON or request-scoped SSE; long-lived notifications use `subscriptions/listen`; old GET/DELETE `/mcp`, session id and resumable Last-Event-ID are removed. | Each POST carries `MCP-Protocol-Version` and `Mcp-Method`; `tools/call`, `resources/read` and `prompts/get` also carry `Mcp-Name`. Header values must match the body; Accept must support JSON and SSE. Modern Streamable HTTP does not define client-to-server notifications. |
| [Multi Round-Trip Requests (MRTR)](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr) | `InputRequiredResult` embeds `inputRequests` and/or `requestState` in the original `prompts/get`, `resources/read` or `tools/call` result; client answers and retries with a new JSON-RPC id. | `requestState` is opaque and must be echoed unchanged. Server must integrity-protect it, bind it to principal/expiry/original request and prevent replay across requests. Input requests must be within client-declared capabilities. |

## 6. Protocol and implementation checks

- **Two eras:** `2025-11-25` and earlier use `initialize`/`initialized` and may use `Mcp-Session-Id`; `2026-07-28` uses per-request `_meta`, no protocol session and no initialize handshake. Do not infer protocol session semantics from an SDK class named `ClientSession`.
- **Metadata trust:** `protocolVersion` and `clientCapabilities` are per-request metadata; `clientInfo` is optional and self-reported. Never use clientInfo/serverInfo as authentication, authorization or trust signals.
- **Discovery:** server must implement `server/discover`; client may call it before business requests. A client can also send a request directly and handle `UnsupportedProtocolVersionError` with the supported-version list.
- **HTTP headers:** `MCP-Protocol-Version` must match `_meta.protocolVersion`; `Mcp-Method` must match the JSON-RPC method; `Mcp-Name` is required for the specified name/URI-routed methods. Gateway routing headers must be checked against the body.
- **Subscriptions:** `list_changed` and resource/task notifications require the modern `subscriptions/listen` stream; they are not the old GET `/mcp` SSE endpoint.
- **Caching:** `ttlMs=0` is immediately stale; `cacheScope=public` is only for caller-independent results; `private` is authorization-context scoped. ACL must be enforced even on cache hits.
- **MRTR:** only `prompts/get`, `resources/read`, `tools/call`; `requestState` is opaque, echo unchanged, short-lived and principal-bound; retries use a new JSON-RPC id. Intermediate input-required results and retries are not cacheable.
- **OAuth:** MCP Authorization is optional and HTTP-only. OAuth 2.1 draft-17 (updated 2026-10-30) and CIMD draft-03 (published 2026-11-02) are Active Internet-Drafts, not RFCs. `resource` binds both authorization and token requests; issuer and audience validation prevent mix-up and token passthrough.
- **Extensions:** Tasks and MCP Apps are optional; both peers must opt in. A task cancellation is cooperative. MCP Apps UI runs in a sandbox and Host controls tool access.
- **Deprecation:** Roots, Sampling, Logging, DCR and legacy HTTP+SSE are deprecated. Elicitation remains the current user-input capability; deprecated Sampling/Roots must not be treated as new-implementation dependencies.
- **Business correctness:** protocol result success does not prove the intended external state transition; verify postconditions, audit authorization and reconcile side effects after timeout.

## 7. Review conclusion

All 24 M12 source occurrences were matched to the current MCP specification, official extension documentation, IETF drafts, OWASP and HTTP/JSON-RPC standards. The key architectural correction is the explicit split between legacy handshake/session and modern stateless request envelopes. The module now aligns transport, caching, MRTR, OAuth, Tasks, MCP Apps and deprecation guidance with the 2026-07-28 specification. The OAuth 2.1 and CIMD documents are clearly identified as drafts, not final RFCs. A follow-up review also limits Tasks task-augmented execution to `tools/call` per the current extension overview, and records MCP Apps as progressive enhancement with Host capability declaration and ordinary-result fallback.
